How content gets from MarketWorks to marketworks.in

Three places, two bridges, and a six-step journey for every piece. This is the architecture we landed on for the content bridge — the visual decoder for everything in tasks/content_bridge/.

As of 31 May 2026 · branch: bridge (kite-lab)
The three places

Each one has a job. None of them do the others' job.

You have two repos on your machine. The marketing surface lives inside one of them (the dashboard). Together that's three distinct "areas" with three distinct jobs.

The engine
kite-lab
~/kite-lab/
The substance. Your portfolios, daily data pipeline, insight engine, backtests, FastAPI backend.
  • 4 live portfolios (TL25, OM25, L6, COMBO)
  • Daily quant note (postclose / premarket / weekly)
  • Insight engine: regime, stress, sectors, watchlists, calendar
  • Knows nothing about content or marketing
The factory
finance-content-os
~/finance-content-os/
The editorial engine. Brand voice, schemas, skills, design system, Remotion compositions — your content production line.
  • 7-stage pipeline (Signal → Insight → Hook → Script → ...)
  • 11 schemas, 10 skills, 2 subagents
  • Brand: voice, pillars, design tokens, compliance rules
  • Knows kite-lab only as a file path it reads from
The storefront
kite-dashboard
~/kite-lab/kite-dashboard/
The marketing surface — Next.js, deploys to Vercel, serves marketworks.in. The public pages where finished content lives.
  • Authenticated product (existing): client portfolios, insights
  • New public routes: /library, /library/<slug>
  • Reads finished content at build time from a sync'd folder
  • Knows finance-content-os only as build-time data
The two bridges

Two thin one-way streets between the three places.

A "bridge" is a small script that copies a specific kind of file from one place to another. They are one-way — nothing flows backwards. And they only deal in files, never in shared code. That's what keeps the three places independent.

Bridge 1
Engine → Factory
kite-lab → finance-content-os
"Here's something interesting that happened in the market today." The engine packages a daily reading or portfolio change into a single tidy file that the factory can read.
Publisher: kite-lab/scripts/publish_signal.py
Drop-off point: kite-lab/data/published/signals/
Importer: finance-content-os/bridge/import_from_marketworks.py
Carries: a Signal — see glossary
Bridge 2
Factory → Storefront
finance-content-os → kite-dashboard
"Here's a finished piece, ready for the web." The factory takes a fully-developed content pack and writes the web-ready version into the dashboard so the next deploy puts it live.
Publisher: finance-content-os/scripts/publish.py
Drop-off point: kite-dashboard/src/marketing-content/ + public/marketing-content/assets/
Consumer: the Next.js build, at build time
Carries: a PublishedPiece — see glossary
Where content comes from

Three origins, one pipeline.

The bridge from kite-lab is just one of three ways a piece can start. Whichever way you start, everything from the content pack onwards is identical — same skills, same publish, same /library URL. The factory was always shaped for this.

Origin 1 · from the engine
Bridge-imported
kite-lab → factory
Pieces grounded in MarketWorks' own data — your moat. Auto-suggested by what the insight engine surfaced today.
  • Daily reading commentary (drift mode, sector rotation)
  • Portfolio rebalance pieces (TL25 / OM25 changes)
  • Cross-asset moves picked up by the engine
  • signal_type: momentum · portfolio · rotation · event
Origin 2 · from your read
Market commentary
founder → factory
Time-sensitive pieces where you have a take the engine doesn't surface — usually news, policy, or sentiment-driven.
  • "What the RBI move means for retail"
  • "Why this rally is different from 2021"
  • "Three FII flow misconceptions"
  • signal_type: news · event · historical
Origin 3 · from your backlog
Evergreen + marketing
founder → factory
Pieces with no time pressure — term lessons, frameworks, and marketing content about MarketWorks itself.
  • "What is Sharpe ratio" (term lesson, 20–30s)
  • "How Trend Leaders picks stocks" (product story)
  • "How RERA reshaped Indian real estate" (informational)
  • signal_type: definition · historical

Journey of one content piece

From "the market did something interesting" to a live URL.

Six steps. Two human gates (you decide before continuing). This is the "from the engine" version; the founder-originated paths skip the bridge import (steps 1–2) and start at step 3 with a signal you created yourself. Everything from step 3 onwards is identical.

1
The engine produces a daily reading
Engine (kite-lab) · automatic

After market close, your insight engine has already built a "MarketReading" — regime, stress, sector RS, watchlists, conditional distributions. The Daily Quant Note assembles this into a paragraph + chart bundle.

What you see: nothing new. This is what your pipeline already does. Postclose runs by ~4:15 PM IST.
2
You publish that reading as a Signal
Engine (kite-lab) · one command

You run the publisher and it writes one JSON file describing what was interesting in plain "this is the headline + the numbers" form.

You run: python scripts/publish_signal.py from-daily-note --date 2026-05-31 --mode postclose
Result: a file appears at data/published/signals/2026-05-31_postclose_note.json
3
The factory imports the signal into a content pack
Factory (finance-content-os) · one command

You switch to a Claude Code session in the content repo and run the importer. It validates the signal, scaffolds a new content pack folder, and registers the topic in the index.

You run: python bridge/import_from_marketworks.py --signal 2026-05-31_postclose_note.json --slug may31_drift_mode
Result: a new folder at data/content_packs/may31_drift_mode/ with the signal lifted into it.
4
The pipeline turns the signal into a finished piece
Factory (finance-content-os) · several skills

In that same Claude Code session, you run the skills one at a time: /generate-insight → /generate-hooks → /write-short-video-script → /repurpose-content → /growth-review → /review-finance-content. Each one reads the previous output and writes its own.

What lands in the pack: insight.json, hook_set.json, script.json, compliance_report.json, plus a finalize step that exports script.md + pack_summary.md and renders thumbnails / carousel PNGs.
5
You approve, then the factory publishes to the storefront
⏸ Founder gate · then one command

You read the finished pack. If anything looks made-up, off-voice, or shaky, you stop and fix it here — not later. Once you approve, the publish script writes the web-ready version of the piece into the dashboard repo.

You run: python scripts/publish.py --slug may31_drift_mode
Result: piece JSON + asset PNGs land in kite-dashboard/src/marketing-content/ and kite-dashboard/public/marketing-content/assets/.
6
You commit + push, Vercel deploys, piece is live
⏸ Founder gate · then git

Commit the changes in both repos, push them, and Vercel auto-deploys the dashboard. Within ~3–5 minutes, marketworks.in/library/may31_drift_mode is a real URL with the piece on it.

Live result: a public, indexable page at marketworks.in/library/<slug>, listed in marketworks.in/library.
Glossary — decoder for the new words

If a term feels jargon-y, it's probably right here.

Every word in plain English. Each of these is a real concrete file or folder on your machine.

Signal

A short JSON file that says "here's what happened, here's why it's interesting, here's the numbers." It's the unit that crosses Bridge 1. Roughly one page of structured notes.

Content pack

A folder named after a topic slug, containing everything for one piece: the signal, the insight, the hooks, the script, the compliance check, the rendered images. Living workspace for one content piece. Lives at data/content_packs/<slug>/.

Pipeline

The 7-step process the factory runs on a content pack. Not a single script — a sequence of Claude Code "skills" you invoke one at a time, each writing its output back into the pack folder.

Skill

A Markdown file at finance-content-os/skills/<name>/SKILL.md that tells Claude how to do one specific job — generate hooks, write a script, run compliance. You invoke them by typing /skill-name in a Claude Code session.

PublishedPiece

The web-ready form of a finished content pack. One JSON file with the title, hook, body paragraphs, takeaway, CTA, and asset paths. What the website actually renders. Lives at published/pieces/<slug>.json.

Manifest

A small index file — "here is the list of everything that exists." The signals folder has one; the published folder has one; the dashboard has one. Each lists what's there, sorted by date. Consumers read the manifest first.

Bridge

A small script (publisher) + a stable drop-off folder + a small script (importer/consumer). Together they copy files from one place to another, one-way. No shared code, no live API calls between repos.

/library

The new public route on marketworks.in where finished content lives. The index page lists pieces by pillar; each piece has its own URL at /library/<slug>. Public — no Clerk login required.

Pillar

The editorial category a piece belongs to — momentum, portfolio construction, active frameworks, investor mistakes, backtest realism, practical education. Used to group pieces on the library index page and to keep your output diversified.

Founder gate

A point in the journey where you stop and decide before the process continues. Two of them: (1) after the insight, you check numbers are real; (2) before publishing, you read the whole piece and approve.

Origin

How a content piece starts. Three options: from the engine (the bridge), from your read of the market (commentary), or from your backlog (evergreen + marketing). All three end at the same place — a content pack — and run the same pipeline from there.

Topic backlog

A flat markdown file at data/memory/topic_backlog.md listing term lessons, marketing angles, and informational topics you want to publish someday. Optional but recommended — removes the "what should I write today?" friction on publish days.
